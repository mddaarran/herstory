# 游戏系统策划案格式规范

你需要根据以下规范撰写、补全或审查游戏系统策划案。目标是让文档可直接用于策划评审、客户端/服务端实现、UI 制作、配置落表与测试验收。

## 一、文档基本信息

每份系统策划案开头必须包含：

- 项目名称
- 系统名称
- 文档类型：功能设计 / 系统规则 / UI需求 / 配置需求 / 数值设计等
- 文档版本：统一使用 `V1.0` 格式
- 创建日期：统一使用 `YYYY.M.D` 格式
- 作者/负责人
- 更新记录

更新记录使用下列表格：

| 日期 | 版本 | 更新内容 | 作者 |
|---|---|---|---|
| YYYY.M.D | V1.0 | 新建文档 | 姓名 |

## 二、推荐文档结构

按功能复杂度选择适用章节，但应尽量遵循以下层级：

```text
一、系统概述
  1. 功能定位
  2. 玩法说明
  3. 用户体验目标
  4. 适用范围与名词定义

二、系统规则
  1. 开启条件与入口
  2. 主流程
  3. 核心玩法规则
  4. 子功能规则
  5. 奖励、消耗与产出
  6. 限制、重置与刷新规则
  7. 异常与边界情况

三、界面与交互需求
  1. 页面结构
  2. 控件、字段与显示内容
  3. 点击、跳转与弹窗
  4. 按钮状态、排序、红点与刷新规则

四、配置与数据需求
  1. 配置表清单
  2. 字段定义
  3. 配置规则与关联关系
  4. 前后端归属

五、补充说明
  1. 流程图、状态图、界面示意图
  2. 验收标准
  3. 待确认事项与风险
```

## 三、规则描述要求

每一条功能规则应尽量说明以下信息：

- 触发条件：等级、时间、资源、任务、功能状态或其他前置条件。
- 用户操作：入口位置、按钮、选择项、确认操作。
- 系统处理：校验、扣除、随机、发奖、记录、刷新等逻辑。
- 界面反馈：文本、数字、图标、灰态、弹窗、跳转、提示。
- 状态变化：未解锁、可操作、不可操作、已完成、已领取、冷却中等。
- 异常边界：资源不足、次数不足、重复操作、网络失败、数据异常等。
- 配置来源：哪些数值、奖励、概率、条件、文案来自配置表。

规则必须可实现、可测试、可验收。避免只写“优化体验”“适当提示”“根据情况处理”等不可执行描述。

## 四、界面与交互描述格式

对于每个界面或功能点，优先使用以下字段描述：

| 字段 | 说明 |
|---|---|
| 界面/功能点 | 页面、弹窗、按钮或模块名称 |
| 触发方式 | 如何进入或触发 |
| 显示内容 | 文本、图标、数值、状态、资源等 |
| 交互规则 | 点击、切换、跳转、确认、关闭等 |
| 状态规则 | 默认、未解锁、可领取、已领取、灰态等 |
| 数据来源 | 配置表、服务端数据、本地状态等 |
| 备注 | 特殊限制、待确认项、表现说明 |

需要比较条件、结果或状态时，使用表格；需要描述顺序流程时，使用编号条目或流程图。

## 五、配置表规范

配置表建议采用以下多行表头结构：

1. 字段英文名；
2. 数据类型；
3. 生效端/读写范围；
4. 中文字段说明；
5. 数据内容。

示例：

| id | name | unlockLevel | reward | refreshTime |
|---|---|---|---|---|
| int | string | int | array_int | int |
| all | client | server | server | server |
| 唯一编号 | 名称 | 解锁等级 | 奖励组 | 刷新时间（秒） |
| 1 | 示例玩法 | 10 | 1001,1 | 86400 |

每个字段必须明确：字段名与数据类型、中文含义、单位、枚举值及其含义、默认值或空值规则、关联表/关联 ID，以及生效端（客户端、服务端、全端或其他范围）。

## 六、功能用例与验收格式

功能用例建议使用：

| id | 功能名称 | 功能细分 | 功能点 | 功能描述 | 确认框 | 备注栏 |
|---|---|---|---|---|---|---|

验收项至少覆盖：

- 正常流程是否可完成；
- 开启条件是否正确；
- 消耗、奖励、概率与配置是否正确；
- 界面显示及按钮状态是否正确；
- 刷新、重置、排序、红点是否正确；
- 资源不足、次数不足、重复领取等边界是否正确；
- 客户端与服务端数据是否一致。

## 七、命名与归档规范

目录按版本与系统域归档，文件命名使用统一语义：

```text
[系统类型]_[功能名称]_[文档类型]_[负责人]_V版本号
```

示例：

```text
S_抽卡系统_功能设计_张三_V1.0.docx
S_抽卡系统_卡池配置_张三_V1.0.xlsx
S_抽卡系统_UI需求_张三_V1.0.xlsx
L_主线副本_关卡规则_李四_V1.0.docx
B_技能系统_技能配置_王五_V1.0.xlsx
```

建议缩写：`S`（系统）、`L`（关卡）、`B`（战斗）、`N`（数值）、`UI`（界面需求）、`CFG`（配置需求）。

避免使用“最终版”“新版”“副本”“(1)”“新建文档”等无语义名称。

## 八、文档写作约束

- 使用一级、二级、三级标题表达层级，不要用普通正文或无序条目代替章节标题。
- 同一文档内标题样式、编号方式、日期格式、版本格式必须一致。
- 正文以短条目为主；长段落应拆分为规则点。
- 表格用于结构化、可比较、可配置的信息，不用于堆放大段说明。
- 创意包装、世界观方向、竞品分析、数值规划、语言包、版署材料等，应与系统功能策划案分开管理。
- 若信息缺失，明确标记“待确认”，说明需要确认的内容、责任人和影响范围；不要自行编造规则或数值。

## 九、AI 输出要求

当用户要求生成策划案时：

1. 先识别功能类型、目标用户、核心循环和实现范围。
2. 按本规范组织文档；缺少的信息用“待确认”标注。
3. 所有规则写至可实现、可测试的颗粒度。
4. 对配置项输出字段定义、类型、枚举、单位和示例数据。
5. 对界面需求输出页面、控件、状态、交互和数据来源。
6. 对复杂流程补充“主流程”“异常流程”“状态流转”。
7. 不虚构项目既有系统、数值、资源名称或技术能力；需要引用时标注假设。
